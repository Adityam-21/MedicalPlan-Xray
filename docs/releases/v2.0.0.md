# v2.0.0 — Audit, rebuild, and an honest number

**Live demo:** https://medical-plan-xray.vercel.app ·
**API:** https://medicalplan-xray-api.onrender.com/model ·
**Model card:** [docs/model_card.md](../model_card.md)

v1.1.0 shipped a tuned XGBoost + SMOTE pipeline, a "Production-Ready" badge, and a model card
claiming **87% F1**. I went back to verify that number and could not reproduce it. This release is
what came out of the audit.

Every figure below comes from `python -m src.train evaluate` in this repository. Raw output:
[`reports/cv_results.json`](../../reports/cv_results.json).

---

## What the audit found

**1. The headline metric was measured on the data it was tuned against.**
The Optuna objective scored each trial with `f1_score(y_test_xgb, ...)`. Hyperparameters were
therefore selected using the test set, which makes the resulting score optimistic by construction.
Nothing in the repository produced 87% — the stored artifact said 0.796.

**2. A fixed bug with no test behind it.**
`class_mapping.pkl` held `{0: High, 1: Low, 2: Medium}`, which is correct for alphabetical
`LabelEncoder` ordering. But nothing asserted it, and the notebook smoke test that appeared to
confirm it was passing categories the encoder had never seen, so every prediction came back High.
It would have looked identical with the mapping reversed.

**3. Tests that could not fail.**
The suite checked that the response had the right keys and that probabilities summed to 1. A fully
scrambled label mapping would have passed both.

**4. Features that earned nothing.**
Gender moved macro-F1 by 0.001 while the labels were gender-skewed: 24.0% of male profiles were
labelled Low against 7.4% of female profiles. `user_id` correlated with the label and was being
dropped by accident rather than intent. The four engineered features moved macro-F1 by 0.001.

**5. A ceiling nobody had measured.**
38 groups of rows have identical inputs and different labels, so **no model can exceed 95.7%
accuracy** on this dataset. Any claim near 100% would have been a red flag.

## What replaced it

### Nested cross-validation

Tuning now runs inside the training folds only, so the search never sees the fold it is scored on.
Re-scored honestly, **the previously deployed configuration gets 0.789 ± 0.033.**

### The simple model won

| Model | Macro-F1 (5-fold CV) |
|---|---|
| **Decision tree, depth tuned (shipped)** | **0.814 ± 0.021** |
| Decision tree, depth 3 | 0.815 ± 0.017 |
| Decision tree, depth 2, spending only | 0.808 ± 0.031 |
| XGBoost, tuned | 0.808 ± 0.028 |
| XGBoost, tuned + SMOTE | 0.801 ± 0.037 |
| Previously deployed config (v1.1.0) | 0.789 ± 0.033 |
| Logistic regression | 0.726 ± 0.026 |
| Random forest, every input **except** spending | 0.719 ± 0.029 |
| Majority class | 0.199 ± 0.001 |

Every gap at the top is smaller than the fold-to-fold standard deviation. A 267-tree ensemble was
not beating a tree two levels deep — it was matching it, while being impossible to explain.

The shipped model fits in three lines:

```
if   spending <= ₹57,163    -> Low
elif spending <= ₹1,39,918  -> Medium
else                        -> High
```

Spending correlates with age (0.61), smoking (0.57) and family size (0.39), so it already carries
most of what the other columns say. Remove it and the best model falls to 0.719.

### The UI now shows the reasoning

Choosing an interpretable model made the product better, not worse. Every result carries:

- the exact threshold that decided it, and the distance to the next tier
- evidence instead of false confidence: "351 of 436 training profiles on this path had Medium"
- close calls flagged as close calls, by probability margin **and** proximity to a threshold
- percentiles, comparable profiles, and per-factor patterns from the training data
- range warnings, including spending above income
- the model's own weakest recall, printed next to the result

### Everything else

- **109 tests** that check predicted values, thresholds, probability ordering and insight panels
- **GitHub Actions CI** on every push: backend tests and frontend build
- **API v2** with `/model` and `/health`; `gender` and `salary_bracket` are still accepted from v1
  clients, ignored, and reported in `notices`
- **Salary bracket derived from income** (979 of 980 rows), so the form stopped asking
- **Runtime image trimmed**: XGBoost, imbalanced-learn, SQLAlchemy and psycopg2 are training-only
- **A rewritten model card** with the confusion matrix, per-tier scores and fairness reasoning
- **Dark theme** and a report-style results layout

## Honest limits

- The dataset is synthetic; nothing here describes a real insurance market.
- **Low tiers are caught 62.6% of the time**, usually misread as Medium.
- Accuracy is 83.4% against a 95.7% ceiling.
- The free-tier API sleeps after 15 minutes, so the first request can take about a minute.

## Superseding v1.1.0

The v1.1.0 notes described a "Production-Ready FastAPI backend" and a "Serialized XGBoost + SMOTE
inference pipeline". Both are retired: there is no production claim without a real SLO, and the
XGBoost pipeline is no longer served. Those notes remain for history.

---

**What I would keep from this:** the bug was not the model, it was that nothing in the repository
could have told me the number was wrong. The tests checked shapes, the tuning scored itself, and
the model card was written by hand. Fixing those three came before choosing any model.
